# ADR-014 — Spouse Negotiation Subsystem

**Status:** PROPOSED — awaiting ratification
**Date:** 2026-07-24
**Change level (ADR-013):** **L4** — new subsystem + financial mutation + new external dependency
**Supersedes:** nothing. **Extends:** ADR-002 (marriage), ADR-003 (hybrid AI pipeline), ADR-004 (simulation)

---

## 1. Decision

After marriage, the spouse becomes an active participant in household finance. Each month from `MARRIAGE_MONTH + 1`, she raises **one proposal** with a cost estimate. The player negotiates it in natural language.

Binding constraint from ADR-003, restated because it is the whole design:

> **The AI never determines a financial outcome.** It extracts intent, voices personality, and maintains memory. A deterministic rules engine decides every rupee.

This keeps the leaderboard measuring financial judgment, not English fluency.

### 1.1 Why she is not merely an obstacle

Proposal *type* is archetype-driven, and **some of her proposals are financially correct**:

| Wife | Proposes | Typically |
|---|---|---|
| The Earner | Lifestyle spend (function, travel, upgrade) | −EV in cash, +satisfaction |
| The Investor | An investment opportunity | **+EV** — refusing costs you money |
| The Saver | A household cost cut | **+EV** — refusing costs you money |
| The Anchor | Insurance / emergency-fund top-up | **+EV in shock months** |

The player cannot learn one rule ("always negotiate her down"). They must judge each proposal on merit — which is the educational point.

## 2. Mechanics

### 2.1 Satisfaction

`spouse_satisfaction` — integer 0–100, starts at **60** at marriage.

- **Primary effect (conversational):** sets how hard she is to convince. Higher satisfaction → she accepts a lower counter-offer.
- **Secondary effect (bounded financial teeth):** household expense drifts by up to **±₹3,000/month** across the full 0–100 range. Deliberately small — it colours the outcome without deciding the game.
- **No separation.** Divorce stays deferred per ADR-002.

### 2.2 The "cannot convince instantly" rule

Directly implements the requirement that persuasion is not a single click:

1. Her opening ask `P` is generated by seeded rules.
2. **Round 1 counter-offers are NEVER auto-accepted**, regardless of amount. She responds, reveals a hint about her floor, satisfaction moves slightly.
3. From **round 2**, a counter `C` is accepted iff `C >= P × min_ratio(archetype, satisfaction)`.
4. Maximum **3 rounds**. Unresolved at round 3 → auto-resolves to her floor, with a satisfaction penalty.

`min_ratio` falls as satisfaction rises: a content spouse compromises; an unhappy one does not.

### 2.3 Closed intent schema (ADR-003 constraint)

Fixed enum, typed params. **Anything unmatched is rejected, never guessed.**

| Intent | Params |
|---|---|
| `ACCEPT_PROPOSAL` | — |
| `COUNTER_OFFER` | `amount: int` |
| `REQUEST_DELAY` | `months: int (1–3)` |
| `PROPOSE_ALTERNATIVE` | `alternative_id: enum` |
| `ASK_QUESTION` | `topic: enum` (free, no financial effect) |
| `REFUSE` | — |

**Confirmation gate:** the extracted proposal is shown back to the player ("You are offering ₹18,000 — confirm?") before the rules engine executes. No money moves on an unconfirmed inference.

### 2.4 Fairness (ADR-000 / ADR-009)

Proposal amount and her floor are seeded on `(user_id, month, archetype)` — reproducible, auditable, and identical for any two players in the same situation. Outcomes depend only on the numbers offered, never on phrasing quality.

## 3. Database migration plan

```sql
-- 1. Satisfaction on the player row
ALTER TABLE public.player_state
  ADD COLUMN IF NOT EXISTS spouse_satisfaction INTEGER NOT NULL DEFAULT 60;

-- 2. Proposal catalogue (admin-authorable, like events)
CREATE TABLE IF NOT EXISTS public.spouse_proposals (
    id BIGSERIAL PRIMARY KEY,
    archetype_id TEXT REFERENCES public.spouse_archetypes(id) ON DELETE CASCADE,
    month INTEGER,                    -- NULL = valid any month
    kind TEXT NOT NULL,               -- lifestyle | investment | saving | protection
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    amount_min NUMERIC NOT NULL,
    amount_max NUMERIC NOT NULL,
    floor_ratio NUMERIC NOT NULL DEFAULT 0.6,   -- lowest share she will take
    ev_note TEXT                                -- why this is or is not a good idea
);

-- 3. Full audit log (ADR-003 mandatory)
CREATE TABLE IF NOT EXISTS public.player_negotiations (
    id BIGSERIAL PRIMARY KEY,
    user_id UUID REFERENCES public.users(id) ON DELETE CASCADE,
    month INTEGER NOT NULL,
    round INTEGER NOT NULL,
    raw_text TEXT,                    -- exactly what the player typed
    intent TEXT,                      -- extracted enum
    params JSONB,                     -- typed params
    confirmed BOOLEAN DEFAULT FALSE,
    rule_input JSONB,                 -- what the rules engine received
    rule_output JSONB,                -- what it decided
    outcome TEXT,                     -- accepted | rejected | pending | auto_resolved
    ai_source TEXT,                   -- llm | template  (fallback observability)
    created_at TIMESTAMPTZ DEFAULT timezone('utc', now())
);

-- 4. Templated dialogue bank (event-day fallback)
CREATE TABLE IF NOT EXISTS public.spouse_dialogue (
    id BIGSERIAL PRIMARY KEY,
    archetype_id TEXT REFERENCES public.spouse_archetypes(id) ON DELETE CASCADE,
    intent TEXT NOT NULL,
    round INTEGER NOT NULL,
    outcome TEXT NOT NULL,
    line TEXT NOT NULL
);

-- RLS mirrors existing player tables: read-own for negotiations,
-- public read for the two reference tables.
```

**Reversible:** every statement is additive. Rollback = drop the three new tables and one column. No existing column is altered.

## 5. Dependency graph

```
POST /negotiate
   └─ ai_service.extract_intent()         ← LLM, 2s timeout
        └─ negotiation_intents.validate() ← closed enum; reject on miss
             └─ [RETURN to player for CONFIRMATION]

POST /negotiate/commit
   └─ negotiation_service.evaluate()      ← DETERMINISTIC. decides the money.
        ├─ constants.min_ratio(archetype, satisfaction)
        ├─ seeded RNG (user_id, month)
        └─ writes player_negotiations (audit)
             └─ ai_service.narrate()      ← LLM or template. NO financial effect.
                  └─ player_state update (cash, satisfaction)
```

**New external dependency:** one LLM API. Isolated behind `ai_service`. If it fails, `narrate()` returns a template line and `extract_intent()` falls back to numeric parsing (`"18000"`, `"18k"`). **The rules path never touches the network.**

---

## 6. Rollback strategy

1. **Feature flag** `game_control.negotiation_enabled` (default **false**). Off = the marriage system behaves exactly as it does today.
2. Disabling mid-event is a single admin toggle; in-flight negotiations auto-resolve at her floor.
3. Code rollback = revert one commit; DB objects are additive and can be left in place harmlessly.
4. LLM outage needs no rollback — the fallback is automatic and logged in `ai_source`.

## 7. Test strategy

| Test | Asserts |
|---|---|
| `test_intent_schema` | Invalid/ambiguous text is **rejected**, never guessed |
| `test_no_instant_accept` | A round-1 counter is never accepted, even at 100% of the ask |
| `test_threshold_monotonic` | Higher satisfaction never *raises* the required offer |
| `test_determinism` | Same `(user_id, month, offers)` → identical outcome across 100 runs |
| `test_cross_player_fairness` | Two players, same archetype/month/offer → identical result |
| `test_no_llm_dependency` | Rules engine passes its full suite with the network **disabled** |
| `test_audit_completeness` | Every committed negotiation writes a full `player_negotiations` row |
| `test_satisfaction_bounds` | Expense drift stays within ±₹3,000 across satisfaction 0–100 |
| `test_ev_balance` | Extend `marriage_ev_sim.py`: negotiation must not break the three fairness gates |

Existing 32 tests must remain green.

## 8. Open questions for ratification

1. **Which LLM provider and key?** Requires an env var on Render and a spend cap. Estimated 3–6 calls per player per month × 12 months × N players.
2. **Should satisfaction enter the leaderboard score?** Proposal: **no** — it is a relationship outcome, not a financial one, and adding it would let a social stat dilute ADR-008. Flag if you disagree.
3. **Is ±₹3,000/month the right size for the financial teeth?**
4. **Free-text input on shared event wifi** — typing speed varies. Should there be a per-round time limit, or is the round admin-gated as today?

---

## 9. Recommendation

Ratify sections 1–7. Answer §8.1 (provider + key) before development starts, because it gates `ai_service`.

**Build order:** rules engine and tests first, with templates only. The LLM layer goes on last, behind the flag — so a working, fair, offline-capable negotiation exists before any network dependency is introduced.
